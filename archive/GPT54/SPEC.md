# GPT54 SPEC

## 1. 文档目的

本文件将 `PRD.md` 中的产品定义压缩为可执行合同，直接约束 AI 编程助理和人类维护者的实现与维护行为。

本文件必须被视为实现依据，而不是实现建议。

除非 `PRD.md` 明确修订，否则任何偏离本文件的实现都应视为 `spec violation`。

## 2. 适用范围

本文件适用于以下内容：

- 仓库结构设计
- 核心文件与目录设计
- 状态管理
- 审计机制
- AI 助手执行协议
- 验收与回归规则

本文件不涵盖以下内容：

- 具体界面设计
- 远程部署架构
- 账号、支付、在线协作等非目标能力

## 3. 实现总则

### 3.1 必须遵守的顶层规则

1. 必须保持原创表达与原创实现。
2. 必须保持核心零第三方依赖。
3. 必须默认本地运行、离线可用。
4. 必须优先使用纯文本和文件系统作为状态载体。
5. 必须使用最小必要结构，不得为未来设想增加抽象层。
6. 必须形成 `观测 -> 判定 -> 执行 -> 校验 -> 回写` 闭环。

### 3.2 明确禁止项

1. 禁止引入数据库作为核心状态基础设施。
2. 禁止引入 Web 服务或前端作为最小版本前提。
3. 禁止依赖外部框架、包管理器和第三方库来成立核心能力。
4. 禁止将重要状态留在聊天中而不写入文件。
5. 禁止让一个文件同时承担知识、任务、审计、决策四种职责。
6. 禁止在未读取项目状态与规则前直接修改文件。
7. 禁止无验证即宣称完成。

## 4. 推荐语言与运行环境

### 4.1 允许的实现介质

- Markdown
- 纯文本
- Python 3 标准库
- POSIX Shell 脚本

### 4.2 禁止的默认依赖

- `npm`
- `pip install`
- 容器作为前提
- 数据库服务
- 消息队列
- 外部 API 作为核心能力依赖

注：如果未来确有扩展需要，必须在不破坏零依赖主路径的前提下作为可选层引入，而非主骨架。

## 5. 规范性术语

本文件中的术语有如下约束含义：

- `必须`：不满足即视为违规
- `应当`：默认必须满足，除非有充分理由记录例外
- `可以`：允许但非必需
- `禁止`：不得实施
- `完成`：满足执行、验证、回写三项条件

## 7. 目录职责合同

### 7.1 `docs/`

职责：承载知识节点、导航文件和人类可读内容。

约束：

- 不得承载项目计划和运行态任务。
- 必须有全局入口文件 `docs/index.md`。

### 7.2 `project/`

职责：承载项目级状态与治理信息。

约束：

- 必须包含项目目标、计划、进展和开放问题。
- 任何重要任务完成后必须同步更新该目录中的对应文件。

### 7.3 `schema/`

职责：承载规则、模板、命名、状态流转和约束。

约束：

- 规则文件必须可被 AI 助手直接阅读理解。
- 规则必须优先于实现。

`schema/ingest.md` 必须定义首次摄入工作流，至少覆盖：

- 节点类型选择
- 节点写入位置
- 索引更新
- 任务记录
- 审计与回写

### 7.4 `audit/`

职责：承载审计基线、快照和报告。

约束：

- 审计结果必须保留，不得只在终端输出后丢失。
- 基线与报告必须可比较。

### 7.5 `runtime/`

职责：承载任务态记录与执行日志。

约束：

- 运行态产物必须可清理，但清理前应已有必要归档。
- 不得把长期知识放入此目录。

### 7.6 `scripts/`

职责：承载零依赖脚本实现。

约束：

- 仅允许标准库实现。
- 每个脚本应只承担一个主要职责。

### 7.8 `CLAUDE.md`

职责：作为发现层入口，把 AI 助手引导到 `schema/`。

约束：

- 必须包含 `GPT54-PROTOCOL-START` 和 `GPT54-PROTOCOL-END` 标记段
- 标记段内必须明确指向 `schema/rules.md`、`schema/node-types.md`、`schema/task-states.md`、`schema/ingest.md`
- 标记段外的内容允许由用户自定义
- 系统更新协议时不得覆盖标记段外内容

### 7.7 `tests/`

职责：承载冒烟测试、夹具和回归验证。

约束：

- 测试必须可在零依赖环境下运行。
- 不允许引入复杂测试框架作为最小版本前提。

## 10. 命名合同

### 10.1 基本规则

1. 文件名必须使用小写英文和连字符，或按项目明确允许的命名风格统一。
2. 同一目录下不得混用多套命名策略。
3. 节点标题可以为自然语言，但文件名应稳定、简洁、可预测。

### 10.2 时间戳规则

如需写入时间戳，统一使用 `YYYY-MM-DD` 或 `YYYY-MM-DDTHH:MM:SSZ`。

### 10.3 任务编号规则

任务编号格式建议为：

### 10.4 审计报告规则

审计报告命名格式建议为：

```text

```

## 11. 状态机合同

### 11.1 状态集合

任务状态必须从以下集合中选择：

- `draft`
- `ready`
- `in_progress`
- `blocked`
- `verify_pending`
- `done`
- `archived`

### 11.2 状态含义

`draft`：仅有意图，尚未具备执行条件。

`ready`：目标、范围、验证方式已明确，可开始执行。

`in_progress`：正在执行。

`blocked`：因规则冲突、信息缺失或验证失败而暂停。

`verify_pending`：执行已完成，等待验证与回写。

`done`：验证通过且已完成回写。

`archived`：任务已结束并归档，不再活跃。

### 11.3 状态迁移规则

- `draft -> ready`：必须已定义目标、输入、输出和验证方式。
- `ready -> in_progress`：必须已读取相关规则与项目状态。
- `in_progress -> verify_pending`：必须已有实际变更或明确执行结果。
- `verify_pending -> done`：必须验证通过并完成状态回写。
- 任意状态 -> `blocked`：当存在冲突、缺失或不可验证结果。
- `done -> archived`：当任务结束且需要从活跃列表移除。

### 11.4 状态违规示例

以下行为视为违规：

1. 未定义成功标准就从 `draft` 进入 `in_progress`
2. 未验证就从 `in_progress` 标记为 `done`
3. 未回写进展就结束任务

## 12. 审计协议合同

### 12.1 审计器目标

审计器是系统传感器。它必须生成可供 AI 助手继续处理的结构化偏差信息，而不是仅供人阅读的散文报告。

### 12.2 最小审计范围

最小版本必须检测：

1. 必需文件缺失
2. 目录位置错误
3. 命名不符合规则
4. `docs/index.md` 未覆盖节点
5. 孤立节点
6. 状态文件缺字段
7. 任务状态非法
8. 审计产物未回写
9. `CLAUDE.md` 缺少 GPT54 协议标记
10. `CLAUDE.md` 与 `schema/` 版本不一致
11. `schema/ingest.md` 缺失

### 12.3 审计输入

最小输入字段：

- `root_path`
- `rules_version`
- `audit_scope`
- `timestamp`

### 12.4 审计输出

最小输出字段：

- `summary`
- `issues`
- `counts`
- `severity_distribution`
- `next_actions`
- `generated_at`

### 12.5 问题对象格式

每个问题对象至少应具备：

- `id`
- `severity`
- `type`
- `path`
- `message`
- `expected`
- `actual`
- `suggested_action`

### 12.6 严重级别

必须支持以下级别：

- `P0`：阻断系统基本运行或导致状态失真
- `P1`：应在当前周期修复的高优先级问题
- `P2`：可延后但需跟踪的问题
- `P3`：优化项或观察项

### 12.7 审计输出示例

```json
{
  "summary": "发现 3 个问题，其中 P0 1 个，P1 2 个",
  "issues": [
    {
      "id": "AUDIT-0001",
      "severity": "P0",
      "type": "missing_required_file",
      "path": "project/plan.md",
      "message": "缺少必需项目计划文件",
      "expected": "存在并包含最小字段",
      "actual": "文件不存在",
      "suggested_action": "创建 plan.md 并写入最小字段"
    }
  ],
  "counts": {
    "total": 3
  },
  "severity_distribution": {
    "P0": 1,
    "P1": 2,
    "P2": 0,
    "P3": 0
  },
  "next_actions": [
    "先修复全部 P0 问题",
    "补齐 project/plan.md",
    "重新运行审计"
  ],
  "generated_at": "2026-05-13T00:00:00Z"
}
```

## 13. 控制器合同

### 13.1 目标

控制器负责把观测结果转化为有顺序的动作，而不是简单展示问题。

### 13.2 决策顺序

必须按以下顺序生成修复优先级：

1. 先修复会破坏基本运行和状态真实性的问题
2. 再修复会阻断后续工作的结构问题
3. 再修复会影响可维护性的关系问题
4. 最后处理优化项

### 13.3 控制输出

控制输出至少应包含：

- 修复顺序
- 每一步影响范围
- 验证方式
- 是否需要人工确认

### 13.4 人工确认触发条件

遇到以下情况必须停下并请求人工确认：

1. 大规模目录重组
2. 覆盖已有结论
3. 删除大量文件
4. 多种解释会显著改变系统边界

## 14. 执行器合同

### 14.1 AI 助手执行顺序

AI 助手执行任务时必须遵循以下顺序：

1. 若存在 `CLAUDE.md`，先读取发现层标记段
2. 按发现层指示读取 `schema/` 规则文件
3. 在维护 GPT54 源仓库本身时，继续读取 `PRD.md` 与 `SPEC.md`
4. 读取 `project/` 状态文件
5. 明确当前目标、成功标准和当前步骤
6. 读取相关目标文件
7. 执行最小必要修改
8. 运行验证
9. 回写 `project/` 状态文件
10. 保存审计或验证结果

### 14.2 AI 助手禁止动作

1. 禁止未读规则即动手
2. 禁止跳过验证
3. 禁止跳过回写
4. 禁止大面积风格化重写
5. 禁止新增与当前任务无关的抽象层
6. 禁止用外部依赖替代协议设计

### 14.3 人类维护者职责

人类维护者至少负责：

- 确认高风险决策
- 审核系统边界变化
- 审核不可逆修改
- 审核开源发布与许可证信息

## 15. 验证合同

### 15.1 验证原则

验证必须贴近当前修改，不得用笼统表述代替实际检查。

### 15.2 最小验证内容

1. 结构验证：文件是否在正确位置
2. 规则验证：是否违反目录或命名合同
3. 状态验证：是否完成状态流转和回写
4. 审计验证：修复后问题是否减少或消失

### 15.3 验证失败处理

若验证失败，任务不得标记为 `done`，只能：

- 回到 `in_progress`
- 或进入 `blocked`

## 16. 测试合同

### 16.1 最小测试集合

最小版本至少应具备以下测试：

1. 初始化冒烟测试
2. 审计冒烟测试
3. 状态机合法迁移测试
4. 审计输出结构测试

### 16.2 夹具要求

`tests/fixtures/` 应包含：

- 合法最小仓库样例
- 缺文件样例
- 命名错误样例
- 状态错误样例

### 16.3 测试命令

最小版本应支持以下可复制命令：

```bash
python3 scripts/init.py --root ./sandbox
python3 scripts/audit.py --root ./sandbox
python3 scripts/verify.py --root ./sandbox
python3 -m unittest discover -s tests
```

进入 `M1.5` 后，应额外支持以下命令：

```bash
python3 scripts/init.py --root ./sandbox --update-protocol
python3 scripts/init.py --root ./sandbox --platform cursor
```

如果实际命令发生变化，必须同步更新 `README.md` 与 `CONTRIBUTING.md`。

## 17. 错误处理与恢复合同

### 17.1 可恢复错误

以下错误应支持规则化恢复：

1. 必需文件缺失
2. 状态字段缺失
3. 节点未入索引
4. 命名不合规
5. 审计报告未落盘

### 17.2 不可直接恢复错误

以下错误必须人工确认：

1. 大规模删除
2. 覆盖既有结论
3. 规则版本回退
4. 项目范围重新定义

### 17.3 恢复策略

恢复必须遵循：

1. 先保全现状
2. 再补最小缺失项
3. 再运行验证
4. 最后更新进展

## 20. 完成定义合同

某项实现只有在以下条件同时满足时，才算完成：

1. 满足 `PRD.md` 中对应目标与范围
2. 未违反本文件中的禁止项
3. 已完成至少一次有效验证
4. 已回写项目状态
5. 如有审计影响，已保存审计结果

## 21. 自检清单

每次重要变更结束后，执行器必须回答以下问题：

1. 我是否先读了规则和项目状态？
2. 我是否只改了当前任务需要改的部分？
3. 我是否留下了可验证的结果？
4. 我是否把结果写回系统而不是留在聊天里？
5. 我是否引入了任何违反零依赖或协议优先原则的内容？

只要有一项回答为“否”，任务就不应标记完成。
