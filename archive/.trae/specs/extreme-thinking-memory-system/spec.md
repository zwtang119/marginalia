# 极致思考：记忆系统的四个压缩层级（v3 — 独立思考版）

## Why

经过多轮分析（Karpathy LLM Wiki、llm-obsidian-wiki SKILL.md、mem0、claude-mem、WeKnora、superpowers、工程控制论审视），我们识别出核心问题：**系统有精巧的结构但没有驱动器，转不起来。** 本文档从工程控制论第一性原理出发，在四个压缩层级上推演系统的最终形态。

**v3 修正**：用户指出"我们不是 Karpathy 模式原教旨主义"。这意味着：
1. 页面类型不应是压缩轴——它是一个设计决策
2. 但也不等于我们一定要 6 种类型——需要从第一性原理独立思考
3. 实际使用数据比理论模型更可靠

## 第一性原理分析：记忆系统需要什么？

### 证据：两个真实项目的使用数据

| 页面类型 | Marginalia (19页) | 美军KB (264页) | 判定 |
|---------|------------------|---------------|------|
| Concept | 9 (47%) | 117 (44%) | **普遍刚需** — 两个项目占比几乎相同 |
| Entity | 0 | 41 (16%) | **领域相关** — 有具体对象的领域才需要 |
| Source | 0 | 98 (37%) | **规模相关** — 有大量原始资料时才需要 |
| Synthesis | 0 | 4 (2%) | **罕见但高价值** — 概念页的特化形式 |
| Comparison | 1 (5%) | 1 (0.4%) | **极罕见** — 本质是带对比表的概念页 |
| Query | 0 | 0 | **从未使用** — 定义了但无人用 |

**关键发现：Karpathy 的 6 种页面类型不匹配实际使用。** Query 是死类型（两个项目 0 页），Comparison 极度稀缺（两个项目各 1 页），Synthesis 罕见（4 页，但高价值）。

### 重新思考：知识的本质形态

从认知科学出发，知识有三个基本形态：

1. **是什么**（Declarative）— 事实、定义、原理 → **Concept**
2. **是谁/有什么**（Referential）— 具体对象、实体 → **Entity**
3. **从哪来**（Procedural）— 来源、过程、决策 → **Trace**

映射到页面类型：

```
概念页 (Concept)
  ├── 定义类：什么是联合目标打击
  ├── 原理类：指挥与控制的工作机制
  ├── 判断类：为什么选择这个架构
  ├── 综合类：[跨源综合] 美军网络战条令体系分析
  ├── 对比类：[对比辨析] F-16 vs MiG-29
  └── 决策类：[选择记录] 为什么用 Schema 不是数据库

实体页 (Entity) — 仅当领域有具体对象时
  ├── 装备：F-35, Patriot
  ├── 组织：US Cyber Command, Joint Chiefs
  └── 系统：Claude Code, mem0

来源页 (Source) — 仅当需要追溯原始资料时
  ├── 文档索引：JP 3-60 联合目标打击
  ├── 论文摘要：某篇研究的关键发现
  └── 会议记录：某次会议的决策
```

**核心洞察：Concept 是唯一的通用类型。Entity 和 Source 是可选的领域特化。**

综合类、对比类、查询类不是独立类型——它们是 Concept 的特殊写法：
- **Synthesis** = 引用了 3+ 来源的 Concept
- **Comparison** = 带对比表的 Concept
- **Query** = 从未实际使用过，不应该是类型
- **Decision** = 记录了选择和理由的 Concept（Marginalia 已有 `docs/decisions/`，证明它有独立价值）

### 独立设计的页面类型体系

| 类型 | 必要性 | 何时激活 | 最小格式 |
|------|--------|---------|---------|
| **Concept** | **核心，永远激活** | 任何知识领域 | 定义 + 核心判断(2+) + [[wikilink]](2+) |
| **Entity** | **可选** | 领域有具体对象时 | 定位 + 核心属性 + 数据 |
| **Source** | **可选** | 有大量原始资料需要追溯时 | 摘要 + 核心知识点(3+) |
| **Decision** | **推荐** | 记录重要选择和理由时 | 选择 + 理由 + 备选方案 |

**不设为独立类型的：**
- Synthesis → Concept 的 `subtype: synthesis`（引用多源的概念）
- Comparison → Concept 的 `subtype: comparison`（带对比表的概念）
- Query → 不设（两个项目从未使用，证明它不是刚需）

### 为什么不用 frontmatter subtype 方案？

虽然技术上可以用 `type: concept` + `subtype: synthesis` 来区分，但实际上：
1. **目录结构比 frontmatter 更直观** — `wiki/syntheses/` 比 `wiki/concepts/` 中带 `subtype` 更容易人工浏览
2. **LLM 创建页面时，目录名比 frontmatter 更不容易遗漏**
3. **但目录结构应该按需创建，不预建空目录**

所以最终设计是：**核心类型（Concept/Entity/Source/Decision）有固定目录，派生类型（Synthesis/Comparison）按需创建目录。**

## 核心公理

1. **知识持久化在 Markdown 文件中**（不是数据库、不是 API、不是向量存储）
2. **LLM 是唯一的读写者**（人类策展来源，LLM 维护 wiki）
3. **控制论闭环必须存在**（传感器→比较器→控制器→执行器→受控对象→传感器）
4. **驱动器必须存在**（有东西强制 LLM 在任务前读 wiki、任务后写 wiki）
5. **页面类型是设计决策，不是压缩变量**（根据领域和规模决定，不因压缩而增减）

## 压缩轴与不变量

```
    压缩轴（可砍的外部工具）              不变量（不可砍的内部模型）
    ─────────────────────              ─────────────────────
    驱动器实现方式（Hook→CLAUDE.md→段落）  页面类型设计（按领域决定）
    传感器精度（5类→3类→LLM自检）         Concept 永远存在
    控制器复杂度（P0-P3→LLM判断）         index.md 导航
    搜索工具（qmd→grep→无）              控制论闭环本身
    稳定性追踪（趋势→人工→无）            读写协议
    前馈控制（有→无）                     反逃避表
    Schema 独立性（SKILL.md→CLAUDE.md）   驱动器存在（形式可变）
```

## 层级三：25% 压缩（Quarter Form）— 最小可用系统

### 压缩原则

砍掉最后一个外部工具（audit_wiki.py），让 LLM 自己做 lint。**页面类型不变**——砍的只是自动化传感器。

| 砍什么（相比50%） | 替代方案 |
|-------------------|---------|
| audit_wiki.py | LLM 自己做 lint，CLAUDE.md 定义 lint 规则 |
| P0-P3 优先级排序 | LLM 自己判断修复顺序 |
| source/ 独立目录 | 可选，小规模时直接从 URL/PDF 摄入 wiki |

**依然不砍的**：页面类型体系、index.md、log.md、读写协议、反逃避表、质量规则。

```

               │  index.md          │
               │  log.md            │
               └─────────────────────┘
```

### 这就是 Karpathy 原始模式 + 独立设计

层级三本质上就是 Karpathy Gist 描述的模式——**一个 CLAUDE.md 文件 + 一个 wiki/ 目录**。没有脚本、没有 Hook、没有搜索工具。LLM 自己做所有事。

但我们的版本比 Karpathy 更精确：
1. **页面类型基于证据**，不是照搬模板（砍掉了 Query 类型，因为从未使用）
2. **有明确的质量底线**，不是"差不多就行"
3. **有反逃避机制**，不是期望 LLM 自觉

### 保留的核心

| 保留 | 不可砍的理由 |
|------|------------|
| **Concept 页面** | 知识的核心载体——砍了就不是知识库 |
| **Entity/Source/Decision（按需）** | 领域特化——按需激活，不预建空目录 |
| **index.md** | 导航入口——没有它 LLM 找不到页面 |
| **log.md** | 操作记录——可追溯 |
| **CLAUDE.md（完整版）** | **系统本身**——这就是产品 |

| 新增/修改文件 | 1 个（CLAUDE.md） |
| 总代码行数 | 0 行 |
| 文档/Schema 行数 | ~150-200 行 |

### 控制论闭环

```
参考输入（CLAUDE.md 中的质量规则）
    → 比较器（LLM 读 wiki 页面，对比规则）
    → 控制器（LLM 判断哪些需要修复）

    → 受控对象（wiki/ 页面）

```

## 层级四：本周完成（Week Form）— 极简交付

### 压缩原则

在层级三的基础上进一步精简：**只做一件事，做到可验证——让 wiki 在一次真实任务中转起来。**

| 砍什么（相比25%） | 替代方案 |
|-------------------|---------|
| 完整的工作流步骤 | 只保留读写两步 |
| 详细的页面类型定义 | 只定义 Concept（核心）+ 提及其他按需 |
| log.md | 依赖 git log |

**依然不砍的**：页面类型的存在（即使极简，Concept 永远在）、index.md、读写协议、反逃避表。

### 系统全景

```
CLAUDE.md（~80 行记忆系统段落）
    │
    ├── 读协议：会话开始读 index.md
    ├── 写协议：任务完成判断新知识 → 写入 wiki → 更新 index
    ├── 反逃避表（4 条）
    ├── 页面类型：Concept(核心) + Entity/Source/Decision(按需)
    ├── 质量底线（断链=0, 有定义, index 覆盖）
    │
    └── wiki/
         ├── concepts/     ← 核心目录，一定存在
         ├── (其他按需)    ← 有就建，没有不预建
         └── index.md      ← 导航入口
```

### 具体交付物

**1 个文件：CLAUDE.md**（追加到已有 CLAUDE.md 的一个段落）

```markdown
## 记忆系统

本项目的知识存储在 wiki/ 目录中。

### 会话启动
1. 读取 wiki/index.md
2. 根据当前任务读取相关页面
3. 说明从 wiki 中知道了什么，再开始执行

### 任务完成
完成任何实质步骤后：
1. 问自己：产生了新知识吗？（新概念、新实体、新决策、新发现、新关系）
2. 如果是 → 写入对应类型的 wiki 页面，更新 index.md
3. 如果不是 → 不做任何事

### 反逃避
| 你的想法 | 事实 |
|---------|------|
| "这个任务不需要查 wiki" | 任何任务都可能从已有知识受益 |
| "没有新知识" | 只要你执行了操作，就可能有发现 |
| "先做完再说" | 做完就忘了，必须立即写回 |
| "wiki 还没有相关页面" | 没有就创建一个 |

### 页面类型

| 类型 | 目录 | 何时创建 | 写什么 |
|------|------|---------|--------|
| Concept | wiki/concepts/ | 总是创建 | 定义 + 核心判断 + [[wikilink]] 关系 |
| Entity | wiki/entities/ | 领域有具体对象时 | 定位 + 核心属性 |
| Source | wiki/sources/ | 需要追溯来源时 | 摘要 + 核心知识点 |
| Decision | wiki/decisions/ | 做了重要选择时 | 选择 + 理由 + 备选 |

综合和对比不设独立目录——它们是 Concept 的特殊写法。

### 质量底线
- 断链 = 0（所有 [[wikilink]] 必须指向真实文件）
- 每个页面有定义
- index.md 列出所有页面
```

### 验证方式

在 US military KB 上执行一次真实任务：

1. **开始新会话** → AI 自动读 wiki/index.md → 说出"我从 wiki 中知道了 X"
2. **执行一个任务**（如"分析联合目标打击的概念"）→ AI 从 wiki 中读取并利用已有知识
3. **任务完成** → AI 识别新知识 → 写入对应类型页面 → 更新 index
4. **下次会话** → AI 读到上一步写入的新知识

**验证标准：第 4 步能成功读取第 3 步写入的内容。闭环成立。**

## 控制论视角的核心洞察

### 闭环在每个层级都存在

| 层级 | 闭环实现 |
|------|---------|
| 层级一 | audit_wiki.py(传感器) → P0-P3(控制器) → LLM修复(执行器) → wiki/(受控对象) → audit |
| 层级二 | audit_wiki.py(传感器) → 优先级规则(控制器) → LLM修复(执行器) → wiki/ → audit |
| 层级三 | LLM自检(传感器) → LLM判断(控制器) → LLM修改(执行器) → wiki/ → LLM自检 |
| 层级四 | LLM自检(传感器) → LLM判断(控制器) → LLM修改(执行器) → wiki/ → LLM自检 |

**层级三和层级四的闭环实现完全相同**——区别只在 Schema 的完备度上。

### 真正的变量只有外部工具的丰富程度

从层级四到层级一，**内部系统（独立设计的页面类型体系）不变**。唯一增加的是外部工具：

1. **行为约束的强度**：从 ~80 行段落到 ~800 行完整 Schema
2. **自动化的程度**：从 LLM 自检到 audit_wiki.py 自动检测
3. **检测的精度**：从"检查断链"到"5类缺陷 + 稳定性趋势"
4. **驱动的可靠性**：从 LLM 自觉遵守到 Hook 强制注入

### 推荐路径

**从层级四开始，用真实任务验证，然后按需向上演进。**

理由：

1. 层级四可以在 1-2 小时内交付并验证
2. 如果 LLM 能可靠地遵守 80 行规则，层级四就够了
3. 如果 LLM 开始逃避规则，增加反逃避表和完整工作流（→层级三）
4. 如果 LLM 自检不够准确，加 audit_wiki.py（→层级二）
5. 如果需要全自动驱动，加 Hook（→层级一）

**每一级解决上一级暴露的具体问题。不提前建设。**

这就是工程控制论的精髓：**先让系统以最简形式运转起来，观察它的实际行为，然后针对观测到的问题逐一增加控制。**

### 架构边界的清晰化

**知识模型是内部系统，实现工具是外部系统。压缩只作用于外部。**

但"内部系统"不等于"Karpathy 的 6 种类型"。内部系统的设计应该基于：
1. **实际使用数据的证据**（不是理论模型）
2. **领域特性的需求**（不是通用模板）
3. **第一性原理的推理**（不是教条复制）

我们基于证据做出的独立设计决策：
- **砍掉 Query 类型**（两个项目从未使用，证明它不是刚需）
- **不设 Comparison 和 Synthesis 为独立类型**（极罕见，是 Concept 的特殊写法）
- **保留 Decision 为推荐类型**（Marginalia 已有 `docs/decisions/`，证明它有独立价值）
- **Entity 和 Source 标记为可选**（使用率取决于领域）
- **Concept 是唯一的通用核心类型**（两个项目占比均约 45%，无一例外）
