# 补充反馈：知识库颗粒度控制论审计（蓝队视角）

> 日期: 2026-05-15
> 关联: openclaw-field-report-2026-05-15.md, memory-md-as-state-vector-2026-05-15.md
> 来源: OpenClaw Agent 对 Wiki 知识库（158 页）的蓝队审计

## 第一项：语言一致性检查

现状：混合语言，结构上是中文，但核心字段是英文。

| 层级 | 语言 | 示例 |
|------|------|------|
| 页面标题 | 中/英混合 | "Computational Decision Space" vs "台海局势CDS分析报告" |
| 文件名 | 英文为主 | `computational-decision-space.md` |
| frontmatter title | 中/英混合 | `title: 台海局势CDS分析报告` |
| frontmatter tags | 英文 | `tags: [policy, CDS, taiwan-strait]` |
| frontmatter related | 英文路径 | `related: [concepts/CDS]` |
| 正文内容 | 中文为主 | 批注、论述、总结均中文 |

结论：对人类可读，但对 AI——中英文混用会造成检索摩擦。当 AI 需要搜索"志伟的创业方法论"时，可能需要尝试"startup" + "创业"两个词才能命中。

## 第二项：工程控制论视角的颗粒度审计

### 分析框架

AI 的认知闭环：`感知输入 → 检索匹配 → 上下文加载 → 推理 → 响应输出`

知识库在闭环中扮演**记忆/先验知识**的角色。颗粒度是否合适，取决于三个维度：

1. 信息密度是否匹配 token 预算？
2. 信息组织是否匹配检索路径？
3. 颗粒度是否足够支撑决策类型？

### 决策类型 vs KB 支撑度

| 问题类型 | 示例 | 当前 KB 支撑度 |
|----------|------|---------------|
| 事实型 | "志伟的核心研究方向是什么？" | ✅ 强（entities/syntheses） |
| 关系型 | "NLUI 和 Polaris 的技术共享点？" | ⚠️ 中（comparisons 有，但 cross-link 少） |
| 判断型 | "志伟现在应该融资还是先做产品？" | ❌ 弱（缺乏决策推导路径） |

### 强项

- `sources/` 的处理方式正确——AI 不需要 PDF 全文，只需快速判断相关性和核心观点
- `concepts/` 中 CDS、MADG、Role DNA 等核心概念定义清晰
- `syntheses/Zhiwei*.md` 能感知本人意图、偏好、当前压力

### 风险点：颗粒度错配

1. **概念层过"教科书"，意图层过薄**：概念页定义方法论，但 AI 真正需要的是用户的具体偏好，而偏好在 memory.md 而非 Wiki——两处割裂
2. **decisions/ 几乎为空（1 个页面）**：决策记录应是 AI 最重要的调用资源，但技术决策散落在各处，未集中沉淀
3. **queries/ 只有 1 个**：高频问答的快速通道几乎没被使用
4. **annotations/ 的价值被低估**：应承担"对话中产生的临时推理结论"的存储角色，否则随 LCM compaction 丢失

### 蓝队评级

| 维度 | 评分 | 说明 |
|------|------|------|
| 语言一致性 | 7/10 | 可用，但增加检索摩擦 |
| 颗粒度-知识层 | 8/10 | sources/concepts 设计合理 |
| 颗粒度-意图层 | 5/10 | 用户偏好分散在多处，无统一索引 |
| 颗粒度-决策层 | 3/10 | 决策记录严重不足 |
| 调用效率 | 6/10 | 页面多但 cross-link 稀疏，检索命中率不稳定 |

### 三个改进建议（按优先级）

1. **建立 decisions/ 的常态化积累机制**：每次涉及"技术选型、战略方向、人员决策"的对话后，主动将结论写入 decisions/
2. **queries/ 填充**：将常见问题固化为 query 页面，实现 O(1) 检索而非 O(n) 全文匹配
3. **修复 memory ↔ Wiki 的割裂**：在检索策略上明确"偏好/意图类 → memory.md" vs "知识/方法论类 → Wiki"的边界
